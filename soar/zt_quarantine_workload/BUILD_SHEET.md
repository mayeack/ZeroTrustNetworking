# zt_quarantine_workload: build sheet

How to put the quarantine playbook on Splunk SOAR 8.7 (cloud): the assets, the roles and users, the custom function, the playbook itself (imported or rebuilt block by block in the visual playbook editor), the Enterprise Security automation rule that starts it, and a pairing checklist.

Files in this folder:

| File | What it is |
|---|---|
| `zt_quarantine_workload.py` | The full-code playbook (SOAR 8.x Python API, Python 3.13). Paste it into a new playbook in full-code mode, or import the package built by `tools/soar_setup.py`. |
| `custom_functions/zt_build_cnp.py`, `.json` | The custom function that builds the policy name, the request bodies and the YAML. Same logic as `ztgen/cnp.py` in the Splunk app (Mode B). |
| `assets.json` | The asset definitions with placeholders for the secrets. |
| `BUILD_SHEET.md`, `BUILD_SHEET.html` | This sheet. |

Setup script: `python3 tools/soar_setup.py` (idempotent; `--dry-run` prints the plan, `--package-only` only builds `local/soar_package/*.tgz`). It creates the roles and users, the assets from `assets.json` with the values of `local/env`, and imports the custom function and the playbook. Ask before running it against SOAR.

## 1. Before you start

- Apps installed on the SOAR (verified on the target): **Splunk** 4.0.2, **HTTP** 4.0.1, **Enterprise Security** connector 6.7.0 (asset `builtin_mc_connector` created by the ES pairing), **Phantom** 3.8.4 (utility app, action `no op`).
- ES 8.7 and SOAR are paired; finding containers arrive with the label `es_soar_integration`. `source_data_identifier` is the ES finding id, `external_id` the ES `event_id`, and the container `data` holds the finding JSON (`name`, `id`, `event_id`, `search_name`/`source`, `normalized_risk_object`, `risk_object`, `risk_score`).
- The stack user `zt-soar` exists (`make users` on the stack; role `zt_soar` inherits `ess_analyst`; password `ZT_PASS_ZT_SOAR` in `local/env`).
- The Kubernetes API emulator answers at `https://zt-k8s.yeackbot.com` with the enforcer bearer token `ZT_K8S_ENFORCER_TOKEN`, and HEC accepts `SPLUNK_HEC_TOKEN`.
- The agent writes its brief into the KV store lookup `zt_agent_briefs_lookup` (fields `finding_id`, `finding_display_id`, `investigation_id`, `investigation_guid`, `workload`, `pod`, `node`, `job_id`, `dest_workload`, `data_class`, `disposition`, `confidence`, `enforcement_point`, `action`, `policy_name`, `blast_radius`, `approver_labels`, `brief_text`, `what_happened`, `run_epoch`). `finding_id` there is the ES `event_id`.

## 4. Custom function `zt_build_cnp`

Home > Custom Functions > + Custom Function (repository `local`).

- Name `zt_build_cnp`; description as in `custom_functions/zt_build_cnp.json`.
- Inputs (all type Item): `namespace`, `pod`, `workload`, `job_id`, `finding_id`.
- Outputs (all type Item, data path = the name): `policy_name`, `label_patch_json`, `label_key`, `label_value`, `cnp_json`, `policy_yaml`, `pod`, `namespace`.
- Code: paste the body of `custom_functions/zt_build_cnp.py` below the "Custom Code Goes Below This Line" marker (the editor generates the signature from the inputs).
- Or import `local/soar_package/zt_build_cnp.tgz` (Custom Functions > Import).

The outputs are what section 12.1 specifies: label patch `{"metadata": {"labels": {"zt-quarantine": "<job id>"}}}`, the CiliumNetworkPolicy `zt-quarantine-<workload>-<job id>` with `egressDeny`/`ingressDeny` to all entities and the labels `app.kubernetes.io/managed-by: zt-quarantine-workload` and `zt/finding: <finding id>`, and the YAML shown to the approver.

## 5. The playbook

### 5.1 Import or paste

- Import: `python3 tools/soar_setup.py` builds `local/soar_package/zt_quarantine_workload.tgz` (`zt_quarantine_workload.py` + `zt_quarantine_workload.json`) and posts it to `/rest/import_playbook` (repository `local`, force update). The JSON envelope is the minimal one derived from a real 8.x export (start and end nodes only); if the imported playbook opens as a visual playbook with two blocks, open it and choose the full-code view, or use the next bullet.
- Paste: Home > Playbooks > + Playbook, repository `local`, name `zt_quarantine_workload`, operates on label `es_soar_integration`, then Playbook Settings > **Convert to full code** (or the code view toggle), replace everything with `zt_quarantine_workload.py`, save. Set the category to `Zero Trust`, active on.

Either way, check the constants at the top of the file: asset names (`zt_splunk`, `zt_k8s_api`, `zt_hec`, `zt_hypershield`, `zt_nexus_nxapi`, `builtin_mc_connector`, `phantom`), the role names (`SOC tier 2`, `NetOps`), the polling cadence (30 s x 12 for the brief, 15 s x 12 for verification) and the prompt time (30 minutes).

Approval message template (format block `approval_message`, parameters in this order: `read_brief:action_result.data.*.finding_id`, `.workload`, `.dest_workload`, `.data_class`, `.disposition`, `.confidence`, `.what_happened`, `.action`, `.enforcement_point`, `.blast_radius`, `build_policy:custom_function_result.data.policy_yaml`, `.pod`, `.label_value`, `.policy_name`):

```
Quarantine request for {0}: {1} reached {2} ({3}).
Agent brief: {4}, {5} confidence. {6}
Recommended: {7} at the {8}. Blast radius: {9}.
Policy to apply:
{10}Approve to label pod {11} with zt-quarantine={12} and create {13}. Reject to close without action.
```

(`{10}` ends with a newline, so the last line follows the YAML directly; the text is identical to `cnp.approval_message` in the Splunk app.)

Behaviour that both modes share (section 12.1): kernel needs one approval from SOC tier 2, DPU and switch need SOC tier 2 then NetOps; the verification search is polled every 15 s for 3 minutes and the first flow found means `verified`; resolution adds the ES note, sets Resolved and the disposition True Positive - Suspicious Activity; one `zt:enforcement:audit` event per state is written as the state happens.

## 6. Start the playbook from Enterprise Security

ES 8.7 starts SOAR playbooks through **automation rules** (Configure > Content > Automation rules), not through SOAR label activation. `python3 tools/es_automation_rule.py` creates or updates the rule:

- Name `Zero Trust Protected Paths`, status on.
- Trigger: finding created by the detection `ZT - Workload Exceeded Risk Threshold on Protected-Path Signals - Rule` (app `DA-ESS-zt_incident_demo`).
- Action: run playbook `zt_quarantine_workload` (repository `local`).

The playbook also runs by hand: open the finding (or its investigation) in ES, Automation tab, Run playbook, pick `zt_quarantine_workload`; or in SOAR open the container and choose Run playbook. Block 1 checks the rule name and title, so running it on any other finding ends with a comment and no action.

## 7. Pairing checklist

1. ES > Configure > SOAR integration (ES 8.5+ documentation): pair the stack with the SOAR; confirm `builtin_mc_connector` appears in SOAR under Apps > Enterprise Security and its test connectivity passes.
2. SOAR > Apps: Splunk 4.0.2, HTTP 4.0.1, Phantom 3.8.4 installed; assets of section 2 created, test connectivity green for `zt_splunk` and `phantom`.
3. `curl -sk -H "Authorization: Bearer <token>" https://zt-k8s.yeackbot.com/version` answers from the emulator; `GET /api/v1/namespaces/build-farm/pods/ci-runner-7d9f8-xk2lq` returns the pod.
4. HEC: `zt_hec` test connectivity (the HTTP app calls the base URL; a 404 on `/` is fine, a 401 is not).
5. Roles `SOC tier 2` and `NetOps`, users `j.chen`, `m.ruiz`, `a.patel`; log in once as `j.chen` to confirm the role sees finding containers (label `es_soar_integration`).
6. Custom function `zt_build_cnp` present and active; playbook `zt_quarantine_workload` present, active, category Zero Trust.
7. `| ztdemo action=config response_mode=soar` (or `make mode-soar`) on the stack so `ZT Response - Request Enforcement` stays out of the way.
8. ES automation rule `Zero Trust Protected Paths` on (section 6).
9. Trial run on the last finding: SOAR container > Run playbook > `zt_quarantine_workload` > answer the prompt as `j.chen` > watch `index=zero_trust sourcetype=zt:enforcement:audit playbook=zt_quarantine_workload` for `requested`, `approved`, `applied`, `verified` and the investigation notes and status.
10. Reset between runs with `make reset` on the stack (removes the policy, the label and the requests) so the next apply returns 201 rather than 409.

## 8. To verify on the live SOAR (marked `# VERIFY:` in the code)

- Name of the Phantom utility app asset (`ASSET_PHANTOM`, default `phantom`).
- `get related investigations for finding` and `start investigations`: the `notable_time`/`finding_times` format and the output field names (`investigation_guid`, `investigation_id`).
- Which prompt result field carries the responding user for an in-product prompt (`action_result.summary.user` is documented for external prompts); the playbook falls back to the action message and then to the role name.
- `update finding or investigation`: the disposition value as a label (`True Positive - Suspicious Activity`).
- `tools/soar_setup.py`: the role permissions payload of `POST /rest/role`, `app_id` on `POST /rest/asset`, `scm`/`force` on `/rest/import_custom_function`, and whether the minimal JSON envelope imports as a full-code playbook (otherwise paste the Python into a new full-code playbook).
