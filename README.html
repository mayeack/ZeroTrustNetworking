Zero Trust Incident demo

A Splunk demo for the deck "One incident, end to end" (zero trust networking). One CI runner pod reaches a protected AI data store. Cisco Isovalent (Cilium Hubble and Tetragon) observes it, Splunk Enterprise Security decides, an Agent Launchpad agent writes the brief, Splunk SOAR or a local approval quarantines the pod at the kernel, and the Zero Trust Fabric Posture dashboard proves the change. Version 1.0.0.

Part What it is
zt_incident_demo/ Main app, display name Zero Trust Incident: the generator (bin/zt_stream.py, bin/ztgen/), the Kubernetes API emulator, the ztdemo, ztsoar, ztbrief and ztevidence commands, the approvals REST endpoint, lookups, KV collections, evidence searches, the posture rollup and the dashboards
DA-ESS-zt_incident_demo/ Enterprise Security content: two risk detections, one finding-based detection, the asset registration

docs/ Field reference, demo script

The five steps: what is generated and what is real

Step What happens Generated or real
1 Connect CI job 88213 starts on pod ci-runner-7d9f8-xk2lq; /usr/bin/curl (parent /bin/sh -c ./scripts/postbuild.sh) connects to checkpoint-store.ai-train.svc:9000 Generated by the app: ci:job:event, Tetragon cisco:isovalent:processExec and cisco:isovalent:processConnect, sent over HTTP Event Collector
2 Observe Hubble egress FORWARDED at bf-node-03, ingress AUDIT at checkpoint-store-1 (identities 48213 and 30719); a new attempt every 30 seconds Generated: cilium:hubble:flow. The verdict of each attempt (AUDIT or DROPPED) is decided from the emulator's real policy state by timestamp
3 Decide Risk +50 and +40 on build-farm/ci-runner; one finding group, risk 90; the agent's brief as a note on the investigation Real: the ES risk detections, the finding-based detection, the Agent Launchpad run (five MCP tools over the Splunk MCP Server), the ES investigation note
4 Enforce j.chen (SOC tier 2) approves; the pod is labeled zt-quarantine: "88213" and the CiliumNetworkPolicy zt-quarantine-ci-runner-88213 is created Real: the SOAR prompt and playbook (Mode A) or the approvals endpoint (Mode B). The Kubernetes API calls go to the emulator, which records them as kube:apiserver:audit
5 Verify The next six attempts are DROPPED (POLICY_DENY, identity 48291); verified; audit trail; coverage 86.4% → 87.9%, unprotected paths 9 → 8, enforcement actions 16 → 17; CI job 88213 fails Generated DROPPED flows from the emulator's state; real verification search, ES resolution (Resolved, True Positive - Suspicious Activity), posture rollup from the data

The background estate is generated too: one cluster ai-platform-dc2, 1,283 workload identities, 92 nodes on fabric dc2, four protected stores with allowlists in audit mode, eight known gaps, about 115,000 events a day at exact daily counts (see the field reference). The background never triggers the ZT detections.

Credentials and settings

Everything comes from the environment or the git-ignored local/env (KEY=VALUE, mode 0600): SPLUNK_URL, SPLUNK_USER, SPLUNK_PASS, SPLUNK_HEC_URL, SPLUNK_HEC_TOKEN, SOAR_URL, SOAR_USER, SOAR_PASS, ZT_EMULATOR_PUBLIC_URL, ZT_EMULATOR_PORT, ZT_K8S_ENFORCER_TOKEN, ZT_K8S_PLATFORM_TOKEN, ZT_AGENT_MCP_TOKEN, generated ZT_PASS_<USER> values, and the LLM provider key for the agent connection (entered in the Agent Launchpad UI, never on disk). Nothing secret is in git, in default/, or in event data. The app's own settings are in default/zt_demo.conf ([hec], [emulator], [stream], [modes]; spec in README/zt_demo.conf.spec); make configure writes the stack-specific values into the installed app's local/zt_demo.conf by REST.

Install order

Run the targets in this sequence. Every target is idempotent; the ones that create users, tunnels or SOAR objects ask first.

make check              # stack, ES, AI Toolkit, MCP Server, KV store, HEC, SOAR, Mac tooling, emulator port
make indexes            # zero_trust and zt_summary
make hec                # HEC token zt_incident_demo (value kept in local/env for the emulator)
make secrets            # emulator certificate (local/certs) and the two bearer tokens (local/env)
make tunnel-install     # Cloudflare tunnel zt-k8s and the DNS route (shows the config, then asks)
make emulator-install   # launchd agents for the emulator and the tunnel; make emulator-status to confirm
make package            # lookups + unit tests + both .tgz + AppInspect (cloud, private_victoria)

Upload zt_incident_demo-1.0.0.tgz and DA-ESS-zt_incident_demo-1.0.0.tgz in Splunk Web (Apps › Manage Apps › Install app from file). Then:

make configure          # HEC URL and the emulator's public URL into local/zt_demo.conf on the stack
make secrets            # again: the bearer tokens into storage/passwords (realm zt_incident_demo), now that the app exists
make users              # roles zt_soc_tier2, zt_netops, zt_agent_mcp, zt_soar, zt_service; users j.chen, m.ruiz, a.patel, zt-agent, zt-soar, zt-emulator
make lookups            # rebuild the CSV lookups from the estate model (only needed after edits)
make sync-objects       # push saved searches, macros, views, lookups and KV configs by REST (between package uploads)
make backfill           # | ztdemo action=backfill hours=24, then a count table by sourcetype
make es-assets          # asset source zt_workload_assets, then a check that assets show on risk events
make mcp-tools          # the five zt_ tools, the zt-agent token, the role policy, one test call per tool
make agent              # Agent Launchpad steps: LLM connection, MCP connection SplunkMCP, agent ZTFlowInvestigator
make es-automation-rule # ES automation rule "Zero Trust Protected Paths" that starts the playbook (Mode A)
make soar-setup         # SOAR roles, users, assets, custom function and playbook (asks first) (verify)
make smoke              # acceptance checks 2 to 8 with a pass/fail table; FRESH=1 right after a fresh install

make help lists every target. make local-install copies both apps into the local Splunk Enterprise at LOCAL_SPLUNK (default /opt/splunk104) as a test bed for the Python code before an upload.

Modes and how to switch

Mode What runs Switch
Response Mode A: SOAR The ES automation rule starts zt_quarantine_workload; the playbook reads the brief from zt_agent_briefs, builds the policy, prompts the SOC tier 2 role, applies through the emulator, verifies, writes the audit trail (executed_by=soar) and resolves the investigation | ztdemo action=config response_mode=soar or make mode-soar
Response Mode B: local approvals (default) ZT Response - Request Enforcement (every minute) opens a request in zt_enforcement_requests and adds the ES note; the Enforcement Approvals dashboard runs | ztsoar action=approve|reject request_id=… comment="…", which calls POST /services/zt_incident_demo/approvals. The endpoint takes the approver from the authenticated caller, checks the caller's roles against zt_approvers, applies with the system token (User-Agent zt-approvals/1.0), and ZT Response - Verify Enforcement verifies and resolves (executed_by=splunk) | ztdemo action=config response_mode=local or make mode-local
Agent mode MCP (default) The finding-based detection's Run AI Agent action starts ZTFlowInvestigator, which calls the five zt_ MCP tools | ztdemo action=config agent_mode=mcp or make agent-mcp (turns the action on, disables ZT Agent - Inline Triage)
Agent mode inline ZT Agent - Inline Triage (every minute) runs the five evidence searches with ztevidence, packs them into one JSON field under 12 KB and runs | aiagent with the evidence in the prompt; remove the MCP tools from the agent in the UI | ztdemo action=config agent_mode=inline or make agent-inline

In both agent modes the brief is captured by ZT Agent - Capture Brief (every minute): it parses index=_audit sourcetype=ai_agent:response, upserts zt_agent_briefs, starts an ES investigation from the finding group if none exists and adds one AI-generated note titled "ZTFlowInvestigator brief".

Fire, reset, cadence, status

Command Effect
| ztdemo action=fire (or make fire) Sends the T0 batch backdated as in the story (CI running at T0 − 27 s, git and /bin/sh execs, curl exec and connect, egress FORWARDED, ingress AUDIT) and saves the plan; the stream then emits attempt k at T0 + 30·k s. Refuses if an incident is in progress or a quarantine policy exists
| ztdemo action=reset (or make reset) Releases the quarantine through the emulator (delete the policy, remove the label; Kubernetes audit user k.osei), writes a released audit event (k.osei (platform), "merge request reverted"), cancels open requests, sets the plan to idle and stamps last_reset_epoch. Every ZT detection, evidence and response search ignores anything before the last reset (zt_since_reset), so you can fire again at once with the same IDs
| ztdemo action=speed value=fast|normal (make fast, make normal) Rewrites the cron of every ZT* scheduled search in both apps. Fast (default): every minute. Normal: every 5 minutes, with the finding-based detection, the response searches and the brief capture offset by one minute
| ztdemo action=status (make status) Checkpoint age, backfill state, plan status and attempt, quarantine state, last reset, cadence, agent and response modes, events sent in the last hour by sourcetype
| ztdemo action=backfill [hours=24] [force=true] Triggers or reports the one-time backfill; force=true only after make reset-hard
make reset-hard Empties zero_trust and zt_summary (delete and re-create the indexes; Splunk Cloud has no clean eventdata), clears the state and backfills again. Asks first
make emulator-start|stop|status The emulator on the Mac; status checks /version locally and through the public hostname

The Cloudflare route for the emulator and how it is protected

The tunnel zt-k8s (~/.cloudflared/zt-k8s.yml) has one ingress rule, zt-k8s.yeackbot.com → https://127.0.0.1:6443 with originRequest.noTLSVerify: true (the emulator's certificate is self-signed), and a http_status:404 catch-all. Only the emulator is routed; nothing on the Mac's Splunk, SOAR or file system is reachable through it. TLS terminates at the Cloudflare edge with a Cloudflare certificate, so SOAR and the app verify TLS ([emulator] verify_tls = 1). Every request must carry one of two bearer tokens generated by make secrets: k8s_enforcer, mapped to system:serviceaccount:soar:zt-enforcer (source IP 10.40.2.18 in the audit), used by the playbook and the approvals endpoint, and k8s_platform, mapped to k.osei, used by reset. Anything else gets 401 and no state change. The emulator implements only what a quarantine playbook needs: GET /version (and /healthz, /readyz, /livez), PATCH of a pod's labels, POST and DELETE of CiliumNetworkPolicies, and the stub paths /hypershield/v1/rules and the Nexus NX-API path for the DPU and switch branches. The MCP Server is not routed through the tunnel: Agent Launchpad reaches the stack's own :8089/services/mcp directly.

Known limits

  • Agent Launchpad needs the Splunk Cloud tenant's AI Toolkit with an LLM connection (OpenAI, Anthropic, Azure OpenAI, Bedrock or Splunk-hosted). Without one, steps 3 to 5 stop at the finding.
  • The brief's wording varies from run to run; the facts (job 88213, !4417, contractor-dev-17, the pod, node, switch port, training job 7712, kernel quarantine, SOC tier 2) may not. The disposition should be true_positive; if the model returns needs_review, rerun the agent manually: | makeresults | aiagent agent_name="ZTFlowInvestigator" prompt="Investigate the newest zero trust finding group and return the brief."
  • Finding IDs differ from the deck's ES-1842: ES assigns its own IDs; the audit trail carries the live one (the investigation's display ID when the finding group has none).
  • After a practice run the posture before-state reflects it for 24 hours (for example coverage 87.9% and 17 enforcement actions before the next fire). Later runs show the same relative changes; the absolute numbers 1,283 / 87.7% / 8 / 2,306 / 16 only hold on a fresh install or after make reset-hard.
  • The Tetragon sourcetypes belong to the Cisco Security Cloud App. Their props are in a marked block of default/props.conf; remove that block if that app is installed later, so its own extractions take over.
  • The cisco:nexus:* sourcetype names may differ from the real Cisco data center networking add-on; rename them in props.conf, eventtypes.conf, the builders and the dashboards if you feed real data.
  • Timings at normal cadence: detections every 5 minutes, the finding-based detection and the response searches one minute later, so expect the finding 6 to 11 minutes after the fire and each later stage up to 5 minutes after the one before (verify).
  • HEC to searchable adds a few seconds on Splunk Cloud; the deck's two searches are expected within 10 seconds of fire.
  • SOAR picks up new findings from the automation rule about every 10 seconds; the playbook then waits for the brief (retrying every 30 s for up to 6 minutes) before it prompts.
  • Verification needs the next attempt (up to 30 s), the stream interval (15 s) and indexing: expect verified 20 to 90 seconds after applied; failed after 3 minutes without a DROPPED flow.
  • Splunk Cloud scheduled searches every minute may skew under load (allow_skew = 0, realtime_schedule = 0 on the ZT searches).

Troubleshooting

Symptom Where to look
Nothing in index=zero_trust after backfill make check (HEC endpoint 200, token present). The stream log: index=_internal source=*zt_incident_demo.log (the file is $SPLUNK_HOME/var/log/splunk/zt_incident_demo.log on the search head). | ztdemo action=status shows backfill_done, the checkpoint age and last_error. A tick that fails leaves the checkpoint where it was and retries 15 s later
KV store errors, zt_demo_state unreadable make check reports the KV store status; the collections are defined in collections.conf and must be readable by splunk-system-user. After a package upload, | inputlookup zt_demo_state_lookup must return one row (_key=global)
Emulator or tunnel down make emulator-status (local /version and the public URL); launchctl list | grep zt-incident-demo; logs in local/logs/ and ~/.cloudflared/zt-k8s-tunnel.log. cloudflared tunnel info zt-k8s. A 401 from the emulator means the token in storage/passwords (make secrets after the upload) or in the SOAR asset differs from local/env
Detections not firing Run each ZT - * - Rule search by hand in SplunkEnterpriseSecuritySuite; check | inputlookup zt_demo_state_lookup for last_reset_epoch (the macros hide everything before it); index=risk source="ZT - *"; the finding-based detection needs both risk events in the Risk data model (| tstats count from datamodel=Risk.All_Risk where source="ZT - *"). At fast cadence all ZT searches run every minute (make fast)
No agent run or no brief Agent errors: index=_internal sourcetype=mltk* OR source=*aiagent* and index=_audit sourcetype=ai_agent:response; the Run AI Agent action must be on (make agent-mcp); the zt-agent MCP token must exist (make mcp-tools); the LLM connection must be set. The capture search reports what it stored: run | savedsearch "ZT Agent - Capture Brief" and read the result column
No request or SOAR prompt Mode B: | ztsoar action=status and | inputlookup zt_enforcement_requests_lookup; the brief must have disposition=true_positive. Mode A: the ES automation rule (make es-automation-rule), the SOAR container for the finding, the playbook run log; response_mode must be soar or ZT Response - Request Enforcement will also open a local request
Approval refused The caller needs role zt_soc_tier2 for the kernel; a refusal writes a refused audit event with the reason. zt_approvers is the matrix
Applied but never verified index=zero_trust sourcetype=cilium:hubble:flow verdict=DROPPED policy_denied=zt-quarantine-ci-runner-88213; the generator decides DROPPED only when the attempt's timestamp is after both the label patch and the policy creation in zt_policy_state (| inputlookup zt_policy_state_lookup)
Posture panels empty index=zt_summary source="ZT Posture - Rollup" must have a row a minute; run the rollup by hand once

Wording rule and account neutrality

Visible text of both apps (event data, field values, dashboards, saved search names and descriptions, the agent prompts and the playbook) never contains the words sample, mock, mockup, fake, synthetic or illustrative. The word demo is allowed in object names (zt_incident_demo, zt_demo_state, ztdemo), in app.conf descriptions, in this README and in docs/. Acceptance criterion 11 greps for the banned words over both apps (event data included, vendored bin/lib/ excluded), the agent files and the playbook. No customer or company names appear anywhere; the only product names are Cisco's (Isovalent, Cilium, Hubble, Tetragon, Nexus Dashboard, Hypershield, Security Cloud App) and Splunk's (Enterprise Security, SOAR, AI Toolkit, Agent Launchpad, MCP Server). Hostnames, users, teams, projects and switches are the neutral canonical values of the story (corp.internal, platform-build, ml-infra/train-utils, dc2-leaf-205).
